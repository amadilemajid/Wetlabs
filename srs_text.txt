Project Context for DevelopersThis document is written for engineers building the WETLABS platform. It prioritises technical precision: API contracts, data models, component responsibilities, tech stack rationale, and acceptance criteria are the core content. Business context is included only where it directly shapes technical decisions.1.1 What We Are BuildingWETLABS is a full-stack platform with three distinct runtime surfaces:SMS/USSD Interface (no internet, 2G GSM) — structured data entry via telecom operator APIsSMS/USSD Interface — structured data entry via telecom USSD gateway. Zero-internet requirement for field users.REST API Backend — Node.js (or Python FastAPI) service layer handling ingestion, validation, business logic, geospatial processing, and external integrations.React Web Dashboard — authenticated SPA for wetland officers, researchers, and administrators. Real-time map visualisation, analytics, and data export.1.2 Core Technical ProblemStandard wetland reporting tools (satellite dashboards, mobile survey apps) require smartphones and internet connectivity. The target population — rural wetland field enumerators — typically has only a basic GSM handset. The WETLABS system must therefore:Accept structured observations over USSD (interactive menu) and SMS keyword commandsParse, validate, geo-tag, and store these observations server-side with no client-side processingSurface the aggregated data through a web dashboard that overlays community reports on satellite-derived wetland indices (NDVI, NDWI)1.3 Technology Stack DecisionsLayerChosen TechnologyRationale Backend APINode.js 20 LTS + Express (or Python 3.12 + FastAPI)Team competency; Developers must ensure steps 1–5 complete within 3 seconds to satisfy the Africa's Talking USSD response deadline.Field user dials shortcode (*384*WETLABS# or equivalent). GSM network routes to Africa's Talking.Africa's Talking sends HTTP POST to ussd-gateway-adapter (webhook). Adapter validates HMAC-SHA256 signature using shared secret from env var AT_USSD_HMAC_SECRET.Adapter determines session state (new vs continuing) via sessionId. For new sessions, initialises session object in Redis with TTL = 180s.Adapter returns USSD response string (max 182 chars) synchronously — this is the menu prompt.On final menu selection (leaf node), adapter publishes WetlandReportDTO to RabbitMQ exchange wetlabs.reports.inbound.report-worker consumes the message. Runs: (a) field validation, (b) wetland code lookup, (c) geo-tagging via geo-service, (d) duplicate check.Validated record is written to wetland_reports table. Worker publishes to wetlabs.notifications.outbound if severity = HIGH.notification-worker dispatches SMS confirmation to reporter's MSISDN via Africa's Talking SMS API.2.3 Request Flow — Dashboard API CallBrowser sends GET /api/v1/reports?wetland_code=KYO&from=2026-01-01&severity=HIGH with Bearer JWT.api-server middleware validates JWT (RS256, public key from env). Checks role claim against route ACL.Controller delegates to ReportService.query(filters). Service builds PostGIS-aware SQL via query builder.Response: GeoJSON FeatureCollection where each feature = one report, geometry = Point(lon,lat).Dashboard renders markers on Leaflet map. Clicking a marker opens a detail panel fetching /api/v1/reports/:id.3.
